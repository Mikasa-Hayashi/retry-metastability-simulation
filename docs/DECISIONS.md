## D-004 | 22.10.2026 | Жизненный цикл запроса: уточнения MODEL_SPEC §2 для кода
- Попытки одного запроса строго последовательны: повтор планируется только после отказа предыдущей попытки (таймаут или немедленный отказ). Поэтому «отмена повторов при успехе» вырожденна: в момент успеха отложенных повторов у запроса нет, а успешной может быть только текущая живая попытка. Ответ после t + T (T считается от начала каждой попытки) не засчитывается.
- Задержка повтора отсчитывается от момента отказа попытки: t_fail = t_attempt + T (таймаут) или t_attempt (отказ из-за полной очереди). Следующая попытка в t_fail + d.
- Отказ при полной очереди: попытка входит, если есть свободный воркер или в очереди < K мест (D-002). Иначе немедленный отказ, повтор по политике.
- Попытка, начавшая обслуживание, дообслуживается целиком (без прерывания), даже если клиент ушёл.
- Доля впустую потраченной работы: сумма времён обслуживания попыток, завершившихся после своего срока (клиент уже ушёл к моменту ответа), делённая на суммарное время обслуживания завершений в окне. Попытки, пропущенные при D = on, времени обслуживания не расходуют.
- Влияет: метрики, V4. Не меняет MODEL_SPEC.

## D-005 | 22.10.2026 | Дисциплины и deadline drop
- FIFO: берётся самая старая запись; LIFO: самая новая; ALIFO: перед выбором, если длина очереди (число записей, включая просроченные) > θ_q·K (θ_q = 0,5, т.е. > 64), берётся самая новая, иначе самая старая.
- D = on: просроченная запись (t_now ≥ срока попытки) пропускается только в момент, когда воркер её достаёт; до этого она занимает место в очереди (буквально по §2 п.6). Следствие, фиксируемое как ограничение: при LIFO/ALIFO в перегрузке просроченные записи на дне очереди могут долго занимать места. Вопрос автору: нужна ли ещё очистка просроченных записей при поступлении новой (это изменило бы модель; без решения не делалось).
- Влияет: D × Q в основной сетке.

## D-007 | 22.10.2026 | Политики R2 и распределения обслуживания
- R2: задержка n-го повтора (n = 1..3) = U · min(cap, base · multiplier^(n−1)), U ~ Uniform(0,1) («полный джиттер»): верхние границы 1, 2, 4 (потолок 16 не достигается при 3 повторах, но параметр сохранён).
- LogN: σ² = ln(1 + cv²), μ = −σ²/2 (среднее 1). Pareto: классическое (тип I) с x_m = (α−1)/α при α = 2,5: среднее 1, cv = 1/sqrt(α(α−2)) ≈ 0,894, третий момент бесконечен (замечание: «тяжёлый хвост» Pareto при α = 2,5 по cv легче, чем LogN cv = 2; это следствие спецификации).

## D-008 | 22.10.2026 | Окно наблюдения, атрибуция метрик
- Каждый первичный запрос относится к окну по моменту первичного прихода. Итоговый исход запроса (успех/неудача) известен не сразу, поэтому симуляция продолжается за конец наблюдения на «хвост» tail (по умолчанию (max_retries+1)·T + сумма максимальных задержек + 1, для базовых политик ≤ 50) при нагрузке последнего сегмента, чтобы все запросы окна успели завершиться без смещения из-за остановки входного потока. Окно g_final = [t_end − 300, t_end), t_end = конец H_rec.
- g(t) для времени восстановления: скользящее окно W = 100, назад от t, по первичным приходам в [t−W, t). Время восстановления = первое s ≥ s0, при котором g ≥ 0,9 на всех точках сетки шага 1 из [s, s+50]; s0 = конец триггера (A) или момент снижения нагрузки (B); цензурируется концом наблюдения (флаг recovery_censored). Из-за трейлингового окна время восстановления не бывает меньше ≈ W при наличии отказов в окне.
- p99: по успешным первичным запросам окна g_final, задержка = от первичного прихода до ответа (клиентская, с учётом повторов). Усиление: среднее число попыток на первичный запрос окна g_final (поле retries_per_request = усиление − 1).

## D-009 | 22.10.2026 | Генераторы случайных чисел
- SeedSequence(seed).spawn(3): потоки входа, обслуживания, джиттера. Вход: время каждого сегмента получается преобразованием времени пуассоновского потока единичной интенсивности (одинаковые базовые экспоненты при разных ρ: общие случайные числа). Время обслуживания и джиттер индексируются номером попытки (k-я попытка берёт k-е число потока), поэтому смена политики/дисциплины не сдвигает потоки.

## D-011 | 22.10.2026 | Оценка порогов (src/thresholds.py)
- Агрегирование по ρ (n_i реплик, k_i отказов). Логистическая регрессия (Ньютон) по ρ; при полном/квазиполном разделении, неположительном наклоне или расходимости — изотоническая регрессия (PAVA с весами n_i), порог — линейная интерполяция уровня 0,5. Bootstrap: непараметрический по репликам внутри каждой точки ρ (эквивалентно k*_i ~ Bin(n_i, k_i/n_i)), число повторов по умолчанию 2000, перцентильный 95 % ДИ; Δ — разность независимых bootstrap-оценок.
- Цензурирование: порог выше максимума сетки (P < 0,5 всюду) = 1,0 (правое, по §6); порог ниже минимума сетки (P ≥ 0,5 всюду) = минимум сетки (левое, симметричное расширение §6, флаг). Δ сообщается без отсечения по 0 (отрицательные значения возможны из-за шума).
